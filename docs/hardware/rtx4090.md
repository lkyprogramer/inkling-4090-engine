# RTX 4090 (sm_89)

This fork runs Inkling 2 Mini on one GeForce RTX 4090. Everything below was measured on one
machine on 2026-11-26; treat it as one data point, not a general guarantee.

| Item | Value |
|---|---|
| GPU | RTX 4090, 24 GB, compute capability 8.9, 128 SMs, 72 MB L2, 99 KB opt-in shared memory per block |
| Host link | PCIe Gen3 x16 |
| Driver | 610.57.04 (CUDA 13.3 driver API), unchanged by the build |
| Toolkit | CUDA 12.8.93 (`nvcc`), installed in a user directory |
| Model | unsloth `Mainline_Support/Inkling-2-Mini-UD-Q4_K_XL.gguf` (NVFP4 ×40, Q8_0 ×154, F32 ×518, BF16 ×32) |
| Draft | `mtp.safetensors` of the native Inkling 2 Mini checkpoint (DSpark, 0.56 GB) |

## Build

```bash
ASTRAL_CUDA_ARCHS=89 NVCC=/path/to/cuda-12.8/bin/nvcc cargo build --release
./target/release/astral hw        # profile sm89, kernel family f80
./target/release/astral selftest  # 93 / 93
```

The toolkit does not need root or a driver change. One way that keeps the driver untouched
is a conda prefix with only the compiler packages:

```bash
conda create -p $HOME/cuda-12.8 --override-channels --strict-channel-priority \
  -c nvidia/label/cuda-12.8.1 -c conda-forge \
  cuda-nvcc cuda-cudart-dev cuda-nvrtc-dev cuda-cccl libcublas-dev cuda-cuobjdump cuda-nvdisasm cuda-profiler-api
```

Do not use the NVIDIA runfile installer or the distribution's `cuda` / `cuda-drivers` packages for
this: both can replace the driver. Do not put the toolkit's `lib/stubs` on `LD_LIBRARY_PATH`; the
stub `libcuda` would shadow the real driver at run time.

## What differs from Hopper

- **Profile.** `ArchProfile::Sm89` maps to the F80 kernel family (`mma.sync` + `cp.async`), with
  FP8 tensor cores reported but not used and no FP4 path.
- **No programmatic dependent launch** (compute capability below 9.0) and **no wgmma** (Hopper
  only). Inkling prefill GEMMs take the `mma3` path; the `mma5` fragment kernels are not wired
  into the Inkling model.
- **Context.** Up to 132,096 tokens (`MAX_CONTEXT`, 128K + 1,024). The 40 sliding-window slots
  keep a ring of `n_swa + max(tmax, 8)` rows rounded up to 64 (3,072 at the default 2,048-token
  prefill chunk), so a prefill chunk never overwrites a row its earliest query still reads and a
  rejected verify row only lands on positions already out of the window; the 8 global slots keep
  the full capacity. `ASTRAL_NO_SWA_RING=1` allocates full-length sliding-window rows instead
  (bit-identical output, for comparison). See [Long context](#long-context).

## Long context

UD-Q4_K_XL, no draft unless noted, one request; measured with the lab's T17 scripts (corpus:
llama.cpp's markdown and Python sources, 310,761 tokens).

| Context | Prompt prefill | Decode | Peak memory | Check |
|---:|---:|---:|---:|---|
| 16K | 3.1 s | 126.9 tok/s | 19,674 MiB | KLD vs llama.cpp `-ub 128` within 2× its own `-ub 1` noise (mean 0.0040, top-1 99.89 %) |
| 32K | 6.5 s | 115.8 tok/s | 20,190 MiB | same (mean 0.0022, top-1 99.90 %); DSpark greedy equals plain for 128 tokens |
| 64K | 14.0 s | 97.4 tok/s | 21,220 MiB | DSpark greedy equals plain for 128 tokens |
| 128K | 31.8 s | 73.7 tok/s | 23,280 MiB | pass key found at depths 0.1 / 0.5 / 0.9 (also at 32K and 64K) |

Within 8K the ring is bit-identical to full-length rows and to the previous build (step, prefill,
decode and DSpark verify passes of 2–8 rows after the ring wrapped). It costs 0.6–0.7 % of
decode speed at 1K–7K tokens (140.6 → 139.8 and 135.4 → 134.4 tok/s).

With the DSpark draft the session fits up to 73,728 tokens of context: the draft keeps FP32 K/V
for its 3 layers at full length (24 KiB per token), and 77,824 runs out of memory.

## Fix found on this GPU

`DeviceBuffer::zeroed`, `DeviceBuffer::copy_from_slice` and `VmmRegion::write` queue a memset or a
pageable host-to-device copy on the legacy default stream and could return before it
completed, while Astral's streams are `CU_STREAM_NON_BLOCKING`. A kernel launched right after
could read a half-copied input or have its output zeroed. On this PCIe Gen3 machine the
self-test failed 3–4 MXFP4 cases with partly zero outputs that changed from run to run. The
helpers now wait for the legacy stream before returning (commit `d17a519`). The bug is not
specific to sm_89.

## Pass count (research)

`ASTRAL_PASSES=R` runs the loop core (layers 6–17) R times instead of the checkpoint's count;
slots, KV, conv state and the attention-residual bank are sized for R, and nothing is reused
across R. Only the varloop research checkpoint (`thinkingmachines/TML-d24-varloop-research`,
`loop_config.is_varloop`, read as `loop.varying`) was trained on several counts (1–5). Loaded
natively, its tensor table equals the unsloth GGUF's (744 tensors, same types and shapes). Token-by-token
log-probs on the llama.cpp-docs corpus (c512 × 8, 2,040 positions):

| Model, passes | Perplexity | KL to the same model at 3 passes (mean) | Decode tok/s |
|---|---|---|---|
| varloop, 1 | 3.667 | 0.041 | 280.6 |
| varloop, 2 | 3.626 | 0.021 | 189.8 |
| varloop, 3 | 3.563 | 0 | 143.3 |
| varloop, 4 | 3.552 | 0.006 | 115.8 |
| varloop, 5 | 3.543 | 0.011 | 96.8 |
| varloop, 6 (outside training) | 3.547 | 0.014 | 82.7 |

The default count is bit-identical to a build without the override.

## Performance

See [Inkling 2 Mini on RTX 4090](../benchmarks/inkling2_mini_rtx4090.md): 156.6 tok/s without a draft
and 172.4 tok/s with DSpark, 2.10× llama.cpp on the same file. Decode runs the fused attention-input
projections with dp4a on this GPU: the int8 tensor-core version reads its weights at about half the
memory bandwidth here (38.4 vs 24.6 µs per layer visit), while on an H100 it was the faster one.
