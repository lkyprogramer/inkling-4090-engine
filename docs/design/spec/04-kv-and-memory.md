# 04 — KV cache and memory management

Requirements: R-KV-1..4. Crates: `mem`, `kvcache`.

## 1. Why typed pools [R]
vLLM's hybrid KV manager unifies all layer types into equal-size pages, which pads mismatched layer ratios, can push attention block size above 400 tokens to match Mamba state, and supports prefix caching for only two groups (one must be full attention). Astral's differentiation: **separate slab classes per cache kind under one byte budget**. Inkling 2 Mini exercises exactly this: sliding-window slots, global slots, per-pass loop KV (confirmed, 48 slots), per-slot short-conv state, and a drafter cache.

## 2. Pool kinds (R-KV-1)
| Pool | Contents | Granularity | Eviction |
|---|---|---|---|
| `GlobalKv` | KV for the **8 global slots** (physical global layers 5, 11, 17, 23; layers 11 and 17 appear in all 3 passes) [L] | token blocks (default 16 tokens `[I]`) | LRU/cost-aware, prefix-shared |
| `SwaKv` | KV for the **40 sliding-window slots**, window 1024 [L] | ring of blocks per sequence; blocks outside the window are freed immediately | freed on window slide; prefix reuse only within window |
| `ConvState` | per-slot short-conv recurrent state (4 sites: K, V, attn-out, FFN-out) [L] | fixed-size per sequence per slot | with sequence; checkpointed for speculation/prefix |
| `DraftKv` | DSpark drafter state (spec 05) | small fixed per sequence | with sequence |
| `VisionCache` | encoded image embeddings (P2) | per image | LRU, content-hash keyed |

**Resolved (spec 06 §2):** llama.cpp allocates **separate KV and conv state per loop pass** while sharing weights, giving 48 cache slots = 8 global + 40 SWA [L; inferred from slot indexing, KV allocation code not read]. Pool definitions are still **parameterised by a `slots: Vec<SlotSpec>` table** generated by `model::slot_to_phys()`, so a variable-loop model (`is_varloop`) or a future Inkling variant is a config change. Passes 1 and 2 restart from the prelude output, so no cross-pass KV sharing or reuse is possible; all slots are pure functions of the token prefix, so prefix caching remains valid per slot.

## 3. Byte-budget arbiter
One `BudgetArbiter` owns the total KV budget and hands slabs to pools by demand with per-pool floors; pools do not reserve fixed fractions up front (that is the padding problem). Policy: SWA blocks are cheap to reclaim (window slide), so under pressure the arbiter reclaims SWA/prefix-cache blocks before preempting a running sequence; global KV is the scarce resource at long context.

## 4. Analytic memory budget (R-KV-2)
`budget = usable_mem − weights − activation_peak(chunk) − graph_pools − workspaces − recurrent/short-conv state − safety`. Computed analytically from the model graph, then verified by a short measured warm-up; this replaces vLLM-style profile-and-subtract [R]. `usable_mem` from spec 01 (discrete vs unified). Admission control refuses requests whose worst-case blocks exceed the remaining budget; preemption policy in spec 05.

Per-token KV (FP16/BF16), `[I]` arithmetic from config/llama.cpp (8 KV heads × head_dim 128 × 2 (K,V) × 2 bytes = 4 KiB per slot-token):
- **Global: 8 slots → 32 KiB/token** (32 GiB at 1M tokens).
- **SWA: 40 slots, window 1024 → up to 160 KiB/token while within window; flat 160 MiB/sequence** once past the window.
- **Conv state:** channels = 2·1024 + 2·2304 = 6,656 per slot × (n_conv−1 = 3). **Measured in llama.cpp's per-op dump (2026-11-23): `cache_r_l0` is 19,968 F32 values per slot** → 78 KiB/slot → ≈ 3.8 MB/sequence over 48 slots (F32). An FP16/BF16 state would halve this; accuracy impact unmeasured.
- Attention-residual `blocks` and loop "messages" are per-token activations within a step, not cached across steps (they are recomputed from the same token's prior layers) `[I]`; confirm in P1.
Capacity example (A100, `UD-Q4_K_XL` 17.6 GB [G]): a short chat sequence costs ≈160 MiB SWA + ≈32 KiB/token global + ≈2 MB state, so >50 GB of KV room on an 80 GB card supports hundreds of concurrent mid-length sequences `[I]`; a 40 GB card leaves ~20 GB after weights/graphs (`[UNVERIFIED]` SKU). 1M-token context [M] on one A100 is bandwidth-bound by global-slot KV reads regardless of capacity (32 GiB read per generated token ⇒ well over 10 ms/token at ~2 TB/s): treat 1M context as a capability to be measured, not a v1 promise.

## 5. Allocator (`mem`)
- **VMM arena** (`cuMemCreate`/`cuMemMap`): reserve a large virtual range; map physical memory in 2 MB granules (stock granularity; 64 KB pages need a patched driver per vAttention [R]). Provides **fixed addresses for CUDA graphs** and cheap growth/shrink.
- Slab classes per pool carve fixed-size blocks from the arena; no per-block `cudaMalloc`.
- **Pinned host pool** for staging/offload; DMA copies preferred over custom copy kernels (vLLM measured 83.4 vs 68.5 GB/s; kernel copies cost ~6% at zero hit rate by taking SMs [R]).
- Fragmentation: fixed-size blocks within a pool; cross-pool rebalance via arbiter at granule level.

## 6. Prefix cache (R-KV-3)
Hash-chained block keys (token ids + model/adapter/quant/loop config hash + vision-content hash). Radix-tree structure for lookup and cache-aware routing hooks (Enterprise edition). Works across `GlobalKv` and `SwaKv` (SWA only for prefixes within the window — documented limitation), and `ConvState` via **checkpoints** at block boundaries (a cached prefix is only reusable if its conv state at the boundary is also stored; cost ≈ 2 MB per checkpoint per sequence `[I]`). Block keys include the 48-slot structure hash. **Cost-aware eviction:** score = recompute_cost × hit_probability / bytes, not plain LRU. Benchmarks must report prefix caching on and off (InferenceX runs it off and understates agentic gains [R]).

## 7. KV quantisation (R-KV-4)
- **A100:** FP16/BF16 KV default. INT8 KV is optional (SHOULD, accuracy measured vs UD-Q8_K_XL baseline); FP8 KV is unavailable on sm_80.
- **H100+/Blackwell (P3, unvalidated):** FP8 KV default with calibrated per-model scales shipped in the model package (uncalibrated scale 1.0 is the documented worst case; vLLM saw a 128k needle test fall from 91% to 13% from an FP8 accumulation bug, repaired to 89% [R]). NVFP4 KV opt-in only: SGLang measured 70 vs 44 concurrent at 32K on one RTX PRO 6000 but −1.6 points on SWE-bench Verified, experimental [R]; agentic/code workloads look most sensitive.
- Lowest-risk first feature: TRT-LLM-style **cold-tier NVFP4** — GPU pages stay FP8/BF16, NVFP4 only in host/disk tiers, quantisation fused into the offload copy [R].

## 8. Offload tiers (P2+)
`StorageBackend` trait: `Host` (pinned DRAM), `Nvme` (GDS/io_uring `[I]`). Offload is a **hit-rate play, not a decode-latency play**; vLLM measured 2–22× TTFT improvement from CPU loads on H100 with async copies [R]; no break-even sourced → ship disabled by default with a measured-hit-rate gate. **GB10: host and device share one pool, so CPU offload adds no capacity; only NVMe does** [R]. NVLink-C2C 900 GB/s is a vendor claim; no measured Grace offload results [R].

## 9. Long context
Sparse/compressed-attention methods address bytes read, not just capacity [R]; none are v1. The model's 4 global layers keep KV growth ~4–6× smaller than a dense 24-layer equivalent, which is the main reason 1M context is plausible at all `[I]`.
